1. Why RSA zig-zags instead of scaling smoothly

Throughput vs. latency graphs in distributed consensus often look “bumpy” because they reflect trade-offs:

Non-monotonic scaling
You’d expect that if you increase batch size (txpb) or push the system harder, throughput should climb while latency grows. But in practice, implementation details, queueing, and protocol thresholds cause inflection points.

Queueing delay effects
At smaller batch sizes, RSA likely has low latency and modest throughput. As you increase txpb, throughput climbs — but once messages start piling up in the pipeline, consensus latency spikes.
→ That’s the jump you see (low → mid → high latency).

Resource saturation (crypto cost)
RSA signatures are heavier than Merkle aggregation. Once the node CPU or network bandwidth starts hitting saturation, throughput gains level off or even dip. But latency can drop again when queues clear at the next stable point.
→ That explains why the line “zigs back” down in latency after a peak.

Protocol behavior
Some protocols have “sweet spots” where batching + signature verification overlap efficiently. Outside those sweet spots, performance gets jagged instead of linear.

3. How to read the zig-zag as “phases” of RSA scaling

Looking at your graph, RSA shows roughly three phases:

Stable zone (low txpb)
Throughput increases moderately, latency stays low.

Stress zone (mid txpb)
System queues build, latency spikes (the “zig up”).

Adaptation / instability zone (high txpb)
Protocol throughput keeps climbing, but latency oscillates. That’s the “zag back” — probably because some batches get efficiently packed, others cause stalls.

This “zig-zag” is not random noise — it’s showing thresholds where system bottlenecks shift (CPU, network, crypto, consensus step).
